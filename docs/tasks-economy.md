# Задания и игровая экономика MVP

## Правила и согласие

Пространство имеет два равноправных места. Задания не создают финансовых обязательств. Нет штрафов, отрицательных XP, рейтинга, ручного подтверждения партнёром или денежных операций.

- **Личное**: один исполнитель — создатель. Партнёр не видит личное задание и его выполнение.
- **Предложение**: один исполнитель — текущий партнёр. Создатель предлагает, только адресат принимает/отклоняет. До принятия экземпляра нет и выполнить невозможно. Создатель видит состояние предложения, но не личный баланс партнёра.
- **Совместное**: создатель согласен при создании; второй участник принимает/отклоняет. После принятия каждый отмечает **только своё** выполнение. Полное завершение требует двух отметок одного экземпляра (0/2 → 1/2 → 2/2).

Пользователь без партнёра может создавать личные задания в solo-пространстве. Сервер сам определяет второго участника; клиент не передаёт user_id исполнителя. Если пространства пока нет, сначала используется существующий экран его создания.

## Центральная конфигурация наград

`task_reward_rules` — единственный серверный источник значений. Клиент читает таблицу для предварительного отображения, но не передаёт сумму в RPC.

| Сложность | XP | Coins |
|---|---:|---:|
| easy / Лёгкое | 10 | 5 |
| normal / Обычное | 20 | 10 |
| hard / Сложное | 35 | 15 |

`task_economy_settings(id=true).together_xp = 20`: дополнительный общий XP после полного совместного экземпляра. Каждый из двух участников отдельно получает личные XP/Coins после своего выполнения. Личные задания и предложения не дают Together XP.

XP и Together XP только накапливаются, Coins пока только начисляются и просматриваются. Они не являются деньгами и не имеют денежной стоимости. Все суммы положительны, totals неотрицательны и ограничены безопасным целым JS (2^53−1). При переполнении вся транзакция откатывается. Никаких списаний, переводов, кошельков, покупок и подписок.

При создании экземпляра значения копируются в `task_instances`: последующее административное изменение конфигурации не меняет уже созданный экземпляр или историю. Новая конфигурация действует на будущие экземпляры. Обычные пользователи не меняют конфигурацию.

## Схема

Миграции: `20261019170000_tasks_economy.sql` и последующая `20261019190000_tasks_security_review.sql`, применяются **после** `20261019150000_auth_profiles_couples.sql`. Вторая миграция усиливает completion RLS и расчёт периода; публичные сигнатуры и типы не меняются.

| Таблица | Назначение |
|---|---|
| tasks | Шаблон, автор, пространство, поля формы, recurrence, status, request_id |
| task_participants | Исполнители и согласие pending/accepted/declined |
| task_instances | Экземпляр периода, снимок наград, статус active/completed/cancelled/expired |
| task_completions | Неизменяемый факт собственного выполнения; unique(instance_id,user_id) |
| user_progress | Личные XP/Coins, доступны только владельцу, сохраняются при выходе |
| space_progress | Накопленный Together XP пространства, доступен его текущим участникам |
| reward_ledger | Журнал положительных начислений с title snapshot и ссылками на экземпляр/факт |
| task_reward_rules, task_economy_settings | Серверная конфигурация, для клиента только чтение |

На всех девяти таблицах RLS. Клиентам не выданы INSERT/UPDATE/DELETE, в том числе на собственные totals, согласия и журнал. Все изменения — только через явно разрешённые RPC. Авторизованный пользователь видит задание, если состоит в его пространстве и является автором или участником. Обычный партнёр не видит чужие личные дела; новая пара не получает доступ к прежней истории заданий. Старый участник после выхода сохраняет доступ к собственным progress и личным строкам reward_ledger, но не к старым таблицам заданий. Заголовок в личной записи журнала — снимок уже разрешённого ему задания.

Исторический Together XP принадлежит пространству: новый партнёр видит накопленный **итог**, но не чужие старые задания или строки их общего журнала. История административного удаления аккаунтов/пространств с каскадами не является пользовательской функцией MVP; обычный клиент не удаляет эти сущности. Удаление аккаунта и процедуры retention требуют отдельного этапа.

## RPC и права

| RPC | Вход / результат |
|---|---|
| create_task | request UUID и поля формы → task UUID. Награда и исполнитель не принимаются |
| respond_task | task UUID, boolean accept → void. Только ожидающий адресат |
| refresh_task_instances | без параметров → серверная календарная дата UTC; создаёт только текущие экземпляры доступных активных шаблонов |
| complete_task_instance | instance UUID → `{already_completed,xp,coins,together_xp}` |
| cancel_task | task UUID → void. Только создатель, правила ниже |
| can_read_task | task UUID → caller-scoped boolean; EXECUTE нужен для RLS |

Все business RPC вызывают `require_verified_user()` (auth.uid + подтверждённый email), SECURITY DEFINER с фиксированным пустым search_path. Anon/PUBLIC не имеют EXECUTE. `materialize_task`, `task_period` и trigger `close_tasks_on_departure` не имеют EXECUTE ни у anon, ни у authenticated. `task-privileges.sql` проверяет эффективные grants с PUBLIC/наследованием и отсутствие прямых прав записи. `can_read_task` — явно разрешённый boolean RLS-предикат, не способ читать произвольные данные.

Порядок блокировок: advisory lock текущего пользователя → row lock пространства → row lock шаблона → row lock экземпляра. Это совместимо с существующими RPC пары и сериализует начисление с выходом второго участника. Все изменения факта, личного журнала, totals, завершения и общей награды выполняются одной транзакцией; любое исключение откатывает всё.

Дополнительные ограничения:

- unique(creator_id,request_id): создание с тем же ключом и теми же полями возвращает прежний id. Другие поля с тем же ключом — conflict. Форма повторно использует ключ при сетевой ошибке; новая форма/изменённые данные означают новое намерение и новый ключ.
- unique(task_id,period_start): один экземпляр шаблона на календарный период.
- unique(instance_id,user_id): одна отметка исполнителя.
- unique(completion_id) и unique(instance_id,user_id) для personal journal: одно личное начисление.
- unique(instance_id) для together journal: одна общая награда.

Повторное выполнение возвращает `already_completed=true` без новых строк/изменений totals. Ответ содержит прежнюю личную награду как справочную информацию; `together_xp=0` означает отсутствие **нового** общего начисления. Повторный ответ уже выполненного участника может быть идемпотентным даже после закрытия экземпляра, пока у него есть доступ к заданию; это не создаёт новых очков. Уже принятый/отклонённый ответ и отмена также повторяемы без новых эффектов. Попытка противоположного решения или перехода из терминального состояния отклоняется.

## Периоды и сроки

- Timestamptz хранится в UTC; календарная зона MVP фиксирована: **UTC**.
- daily: календарная дата UTC. weekly: ISO-неделя с понедельника 00:00 UTC.
- Сервер определяет период по `clock_timestamp()` **после получения блокировок** пространства, задания и (для выполнения) экземпляра. Начало транзакции до полуночи не даёт права выполнить старый период после ожидания блокировки. Для каждой операции над экземпляром календарная дата считывается один раз: переход периода во время последующих записей не разделяет одно начисление на два периода. Клиент не передаёт время/период в complete или refresh.
- due_date у разового задания — дата доступности/выполнения; просроченное разовое дело можно выполнить позже без штрафа. До будущей даты экземпляра нет.
- У повторения due_date — первая доступная дата. Если даты нет, начало — день создания. При позднем принятии предложения материализуется только текущий период.
- refresh при открытии/возврате на экран и polling раз в 15 секунд лениво создаёт текущий экземпляр. После reload результат восстанавливается из БД, а не из localStorage.
- Пропуски не создают дополнительные экземпляры/награды. Неотмеченные прошлые периоды не выполняются задним числом. Незавершённый прошлый экземпляр получает expired при следующем успешном refresh/materialize; отклонённое выполнение старого периода откатывается целиком и само по себе не сохраняет смену статуса; уже заработанная личная награда остаётся. Отметки разных периодов никогда не складываются в Together XP.
- Ежедневное/еженедельное согласие действует на повторяющийся шаблон целиком. Изменение полей/условий после принятия и режим подтверждения партнёром не реализованы: потребуется отдельная модель согласия.

## Переходы и отмена

Личное: active → completed (разовое). Предложение/совместное: pending → active либо declined. Из pending/active создатель может отменить дело. Повторяющийся шаблон остаётся active после завершённого экземпляра; completed относится к экземпляру, пока не прекратятся будущие повторения.

Нельзя вручную отменить текущий частично выполненный экземпляр. Завершённое разовое задание отменить нельзя. Повторяющийся шаблон после завершённых периодов можно остановить, если в текущем активном экземпляре ещё нет выполнения. Завершённые экземпляры и журнал остаются прежними; отмена не списывает очки. Из expired невозможно заработать награду, даже если браузер показывает старую карточку.

При выходе любого участника trigger в той же транзакции закрывает все pending/active предложения и совместные шаблоны пространства, а также личные шаблоны ушедшего. Незавершённые экземпляры получают cancelled, без дополнительных личных/общих наград. Уже выполненные факты/строки журнала не удаляются, XP/Coins остаются у пользователей, Together XP — у пространства. Личные дела оставшегося продолжают работать. Повторное подключение не воскрешает закрытые совместные шаблоны: нужно новое добровольное предложение. `task_participants` сохраняет историческое согласие (в том числе pending); терминальный статус задания имеет приоритет и запрещает дальнейшее принятие/выполнение. Это не активное обязательство и не восстановленное согласие на новое задание.

## UI, кэш и ограничения

«Сегодня»: приветствие, серверные totals, текущие/просроченные разовые дела и текущие повторения, входящие предложения, последние начисления. «Дела»: форма, фильтры, согласие, выполнение, отмена и история. «Мы»: общий progress. Пять основных разделов, Auth, темы и demo сохранены. Demo не начисляет серверные очки и не имитирует синхронизацию/платежи.

Никаких optimistic totals: успех/награда появляются после ответа RPC, затем refetch. Все task query keys включают user id; существующий AuthProvider очищает кэш при смене пользователя/выходе. Создание/вступление/выход из пространства инвалидируют task workspace. При сетевой ошибке можно повторить запрос; stale-состояние не обходит SQL-проверки.

MVP не реализует cron, локальные часовые зоны, редактирование шаблонов, списания, магазин, переводы, рейтинги и anti-farming лимиты на число **разных** личных дел. Выполнение подтверждается самим пользователем. История заданий загружается offset-страницами по 200; UI показывает карточки по 20 с кнопкой «ещё», последние 20 строк журнала и последние 5 достижений. Ограничения и будущая серверная пагинация описаны ниже. Polling 15 секунд даёт eventual consistency между устройствами.

## Ручная проверка на двух аккаунтах после отдельно согласованной миграции

1. На staging (не production) применить новые миграции по `docs/supabase.md`. Переменные прежние; дополнительных ключей нет. Войти A и B в разные браузерные профили, убедиться, что они уже в одной паре.
2. A создаёт личное лёгкое дело: title, category, description. B не должен его видеть. A выполняет: +10 XP/+5 Coins, без Together XP. Reload восстанавливает те же totals; повторная отправка не начисляет снова.
3. A предлагает обычное дело B. До согласия выполнить нельзя; A не может принять за B. B отклоняет: ноль штрафов/наград. Новое предложение B принимает и выполняет: +20 XP/+10 Coins только B.
4. A создаёт сложное совместное дело. B принимает. A выполняет: 1/2, +35 XP/+15 Coins только A, общего начисления ещё нет. B выполняет: 2/2, личные +35/+15 и ровно +20 Together XP. Одновременные/повторные нажатия не меняют суммы повторно.
5. Создать daily и weekly; текущий экземпляр завершить и перезагрузить. Второй награды в том же периоде нет. Для перехода периода использовать отдельную disposable БД/автотесты — не изменять часы/данные облачных пользователей.
6. В «Выполненные» и истории видны подтверждённые факты; в «Мы» — общий итог. Проверить offline/online и обе темы на узком экране. Нельзя отменить частично выполненное совместное дело.
7. На **специальных staging-аккаунтах**, где допустимо менять членство, проверить выход B при незавершённом совместном деле: оно закрывается, личные балансы и старый Together XP сохраняются. Не проводить выход на уже существующей рабочей паре без отдельного согласия.
8. Прямые INSERT/UPDATE/DELETE totals/journal/participants из обычного клиента и anonymous RPC должны отклоняться. Для проверки изоляции третьей пары используйте disposable тесты или отдельно согласованные тестовые аккаунты.

## Ограничение клиентской пагинации и следующий этап

Текущий клиент сначала загружает весь доступный workspace через независимые offset-запросы по 200 строк, а затем показывает карточки по 20. Это не серверная пагинация UI. При конкурентной вставке или изменении видимости между страницами возможны пропуски/повторы: сортировка с id не создаёт общий snapshot. Задания, участники, экземпляры и факты читаются разными HTTP-запросами и могут временно не соответствовать одному моменту времени. Серверные RPC всё равно заново проверяют доступ/статус и не используют эти данные для сумм начисления. Polling даёт eventual consistency, но не гарантирует непрерывность истории; стоимость растёт с полной историей. Алгоритм также предполагает, что Supabase API max_rows не ниже 200: меньший лимит может выглядеть как последняя страница. Последние 20 начислений являются намеренным ограничением интерфейса.

Следующий этап: отдельный серверный feed с keyset-пагинацией `(created_at DESC, id DESC)`, строгим лимитом 1–100, составным индексом и верхней границей первой страницы. Курсор включает версию, позицию, верхнюю границу и фильтры; его нужно валидировать и привязывать к текущему auth.uid()/пространству, никогда не считать источником полномочий. Предпочтительно SECURITY INVOKER SQL RPC с действующей RLS: фильтрация разрешённых заданий должна предшествовать LIMIT, а детали страницы собираться одним SQL-запросом с единым snapshot. Не принимать user_id как доверенную идентичность. Удаление/отмена/изменение членства немедленно меняет доступ даже внутри старого курсора; смена пространства сбрасывает курсор. Для строгого исторического snapshot между HTTP-запросами потребуется отдельная версионированная модель feed, а не обещание snapshot от одного watermark. Текущие экземпляры и история начислений должны иметь отдельные ограниченные endpoint/cursor. Добавить тесты вставок между страницами, одинаковых timestamps, подмены курсора и смены членства.

## Заключительное review PR #3

- Completion RLS явно проверяет `can_read_task(i.task_id)` с квалифицированной ссылкой на факт; отдельный тест расширяет видимость instances только внутри откатываемой тестовой транзакции и подтверждает приватность личных заданий и изоляцию пар.
- Расчёт периода переведён с transaction timestamp на wall clock после блокировок. Daily/weekly тест использует недоступный клиентам clock-fixture только в disposable PostgreSQL, реальное ожидание блокировки, конкурентный refresh и повторные выполнения двух партнёров. Старые личные начисления сохраняются, разные периоды не объединяются.
- Ошибка последнего общего начисления откатывает также личное начисление/факт второго партнёра; конкурентный retry даёт ровно одну награду. Выход, отмена и повторное вступление не воскрешают задания/экземпляры, исторические согласия и награды сохраняются.
- Миграции не применяются к удалённой базе. Для локальной проверки: `npm test`; полноценный Supabase smoke — по `docs/supabase.md`. Bootstrap SQL предназначен только для disposable PostgreSQL, не для реального Supabase.
