# Совместные цели пары — этап 5

## Принципы

Цель — общая мечта двух равноправных участников. Любой предлагает, другой принимает или отклоняет без штрафов. Автор не становится администратором. Цель с отсутствующим партнёром не создаётся; solo-пространство и существующие задания/Coins остаются доступны. Срок — необязательный ориентир, без автоматического закрытия, санкций или напоминаний.

Название 2–100 символов после trim, описание до 1000, категории: путешествия, дом, отношения, здоровье и привычки, обучение, другое. Шесть встроенных emoji, без URL/файлов. Целевая дата 1900–2200, может быть в прошлом. Изменение метаданных цели в MVP не реализовано: условия исходного предложения сохраняются.

## Согласия и жизненный цикл

`pending → active | declined | closed`: при создании автор согласен, второй участник принимает/отклоняет. Автор может отозвать ещё не принятое предложение (closed).

`active ↔ paused`, `active | paused → closed` — только по новому предложению и решению второго участника. `active → completed` — после взаимного подтверждения достижения. Closed/completed/declined терминальны, повторного открытия нет. Прежний участник при повторном вступлении не может возобновить старую закрытую цель.

**Одно ожидающее согласование на цель**: новая цель, добавление/редактирование шага, порядок, пауза, продолжение, закрытие или завершение. Пока предложение pending, новые изменения и отметки шагов временно заблокированы. Адресат может принять или отклонить, автор предложения — отозвать; никаких штрафов. Это простой способ не менять условия после того, как один уже согласился. Отказ от шага/паузы/закрытия не закрывает цель, а сохраняет прежнее состояние.

`goal_consents` хранит неизменяемые параметры предложения и факт решения. Авторство предложения означает собственное согласие, `resolve_goal_consent` разрешён только другому исходному участнику для accept/decline; withdraw — только автору. Терминальные повторы того же решения возвращаются без изменений, противоположное решение отклоняется.

## Шаги и прогресс

- Оба могут предложить новый шаг или изменить ещё не начатый. Title/description и участники вступают в силу только после согласия второго человека.
- Assignment `me`/`partner`/`both` относится **к автору предложения**, сервер сам определяет UUID. В карточке согласования UI показывает конкретных участников, не переносит «Я» адресата на автора.
- До принятия шаг существует только в payload согласования и не входит в прогресс. Для изменения сохраняется тот же step UUID.
- Каждый отмечает только себя. Один назначенный человек завершает одиночный шаг; оба назначенных — совместный (0/2 → 1/2 → 2/2).
- После хотя бы одной отметки title/description/assignment шага менять нельзя. Удаление/undo шагов в MVP отсутствует. Полностью выполненные шаги не получают награды и не создаются заново через редактирование.
- Порядок меняется предложением списка всех текущих step UUID. Сервер проверяет принадлежность цели, полный набор и отсутствие дубликатов; второй участник видит весь новый порядок. Перестановка не удаляет отметки и не влияет на награды. В уже завершённой цели запрещена и перестановка.
- До 100 согласованных шагов на цель; UI ограничивает список, сервер проверяет независимо.

`goal_progress` — PostgreSQL view с **security_invoker=true**: RLS исходных таблиц действует для читателя. Total — число принятых шагов, completed — серверный status после всех собственных отметок. Процент — целая часть completed×100/total. Пустая цель всегда 0%, даже если принята; pending шаги не учитываются. UI не отправляет проценты на сервер и не решает по своему прогрессу, можно ли начислить бонус.

## Достижение и Together XP

Хотя бы один согласованный шаг и все шаги completed: любой участник предлагает complete. Другая сторона подтверждает. Пока complete ожидает решения, нельзя добавить шаг или поменять состояние.

Сервер в одной транзакции:

1. Проверяет обоих исходных действующих участников, доступ, статус active и все шаги.
2. Добавляет ровно одну строку `goal_reward_ledger` с PK(goal_id), **+50 Together XP**.
3. Атомарно увеличивает `space_progress.together_xp` через upsert.
4. Ставит completed и completed_at, принимает consent, добавляет событие.

Любая ошибка, включая ограничение safe integer или COMMIT-time trigger, откатывает **все** изменения. Повтор принятия и параллельные HTTP не создают второй бонус. После completed цель read-only; идемпотентные повторные отметки/ответы могут подтвердить старый результат, но не меняют данные.

За шаги и цели нет личных XP/Coins. `reward_ledger` и `coin_transactions` не меняются: триггер Coins по-прежнему реагирует только на личные начисления заданий. Новый журнал не имитирует task completion. Для обычных пользовательских операций общий итог равен Together XP из task reward_ledger + Together XP из goal_reward_ledger. Новая награда сериализуется с task completion по общей space-блокировке; например, 20 за задание +50 за цель =70, а не потерянное обновление.

Проверка достижения — взаимное решение, не автоматическая отметка только по 100%. Нет auto-complete, reopen, повторного бонуса, рейтинга или ограничения количества разных целей против farming в MVP.

## Схема, RPC и безопасность

Миграция: **`supabase/migrations/20261020090000_couple_goals.sql`**, после всех миграций PR #4. Существующие миграции не переписываются. Миграция создаёт пустую схему и не начисляет бонусов за демоданные или старые задания.

| Объект | Назначение |
|---|---|
| couple_goals | Цель, два фиксированных участника, пространство, статус, дата и create request UUID |
| goal_consents | Одно ожидающее изменение, валидированный payload, автор, решение, request UUID |
| goal_steps | Только согласованные шаги, порядок и status |
| goal_step_participants | Один или два согласованных исполнителя |
| goal_step_completions | Неизменяемая собственная отметка, PK(step_id,user_id), FK к назначению |
| goal_events | Append-only история предложений, решений, отметок и выхода |
| goal_reward_ledger | Один общий бонус 50 за goal_id |
| goal_progress | Caller-scoped security-invoker view, не обходящий RLS |

| Публичный RPC | Контракт |
|---|---|
| create_couple_goal | request UUID, title/description/category/emoji/target_date, p_expected_goals → goal UUID |
| propose_goal_change | goal UUID, request UUID, kind, payload, p_expected_changes → consent UUID |
| inspect_goal_request | request UUID, необязательный goal UUID → собственный найденный результат или null; только SELECT |
| resolve_goal_consent | consent UUID, accept/decline/withdraw → void |
| complete_goal_step | step UUID → void, исполнителя определяет auth.uid() |
| can_read_goal, can_read_goal_step | Caller-scoped bool, нужен RLS |

Step payload: `{title,description?,assignment}`; edit добавляет step_id. Reorder: `{step_ids:[...все UUID...]}`. Pause/resume/close/complete: `{}`. JSON ограничен 20 KB, ключи и типы проверяются. Нельзя передать user_id, XP, цену, trusted status или процент. Goal create проверяет идентичный payload при повторе request UUID; изменение условий тем же ключом — conflict. Goal change также сверяет исходные goal/kind/payload.

Все семь таблиц имеют RLS, для authenticated только SELECT, даже на собственные строки. Public/anon доступ запрещён. Читатель должен быть текущим участником пространства **и** одним из двух исходных участников цели. UUID, чужое пространство или новая пара не дают доступ к чужой истории/шагам/событиям/наградам. View сохраняет эти условия. Бизнес-RPC требуют подтверждённого пользователя, helpers/trigger имеют фиксированный пустой search_path, PUBLIC EXECUTE отозван. Внутренние lock_couple_goal и close_goals_on_departure недоступны anon/authenticated. Audit: `supabase/tests/goal-privileges.sql`.

Порядок блокировок: advisory user → space row → goal row → consent/step row → space_progress. Он совместим с Auth/leave, заданиями и магазином. Операции разных подсистем в одной паре сериализуются по space, не захватывают чужой advisory user lock после space. UNIQUE pending goal, request keys, completion PK и reward PK защищают от гонок дополнительно к состояниям React.

## Выход и история

Trigger в той же транзакции leave закрывает pending/active/paused цели исходной пары и аннулирует pending consent (void). Принятые/отклонённые решения, шаги и события остаются. Уже достигнутые цели/bonus не меняются, Coins/личные XP не затрагиваются. При гонке finish/leave либо finish зафиксировался первым и +50 остаётся, либо leave первым закрывает цель без бонуса.

Ушедший теряет доступ к старым целям. При возвращении того же человека в то же пространство он может снова читать свою историческую цель, но closed остаётся closed. Новый партнёр не видит прежние приватные цели; исторический общий **итог** Together XP принадлежит пространству и доступен его текущим участникам, как в PR #3/#4.

Удаление аккаунта/retention не является пользовательской функцией MVP. FK-cascade позволяет чистить только собственные disposable Auth fixtures в локальных тестах; нельзя применять это к существующим аккаунтам без отдельной процедуры и согласия. Обычный клиент не удаляет события, отметки и ledger; выход их не удаляет.

## UI и ограничения

`/goals` — активные, ожидающие, paused и завершённые/закрытые цели, карточки и форма. `/goals/:goalId` — описание, шаги, согласования с условиями, история, пауза/возобновление/закрытие/достижение. Поддерживаются обе темы, мобильная навигация, offline disable, загрузка/пустое/недоступное/безопасная ошибка с повтором. Поздравление и +50 появляются только из сохранённого серверного completed, без optimistic totals. Неуспешный RPC не изображает бонус.

Query key включает user id; AuthProvider очищает данные при смене аккаунта. Goal actions инвалидируют goals и task workspace (общий XP); изменения членства — также goals. Polling 15 секунд даёт eventual consistency между устройствами. При reload данные восстанавливаются из Supabase, не из localStorage. Demo содержит только обозначенный пример с отключёнными предложениями/наградами, без сессий.

Как текущие задания/магазин, клиент загружает разрешённый workspace offset-страницами по 200 и отображает цели/события порциями по 20. API max_rows должен быть ≥200. Между независимыми HTTP нет общего snapshot, возможны временные пропуски/повторы; сервер повторно проверяет все условия и не доверяет показанному проценту. Для большой истории нужен bounded server keyset feed с RLS и actor-bound cursor по `tasks-economy.md`. В MVP нет cron, файлов, goal metadata edit, step deletion/undo, редактирования начатого шага, параллельных ожидающих изменений или повторного открытия completed.

### Ручная проверка двух аккаунтов

Только на специально разрешённой staging-паре. Checklist не разрешает удалённую миграцию или разрыв рабочей пары.

1. A предлагает цель, B видит pending. A может отозвать; принять за B нельзя. B отклоняет без штрафов. Новое предложение B принимает — active, пустая цель 0% и completion запрещён.
2. A предлагает шаг «Выбрать даты», участники оба. До согласия B шаг не входит в progress. B принимает; каждый отмечает только себя, первая отметка не завершает совместный шаг.
3. B предлагает одиночный шаг для A, A принимает. Только A может отметить его. Один из двух завершённых шагов даёт 50%, все — 100%. Личные XP/Coins не меняются.
4. У неначатого шага предложить title/assignment; до согласия старые условия прежние и отметки приостановлены. Отказ сохраняет их. Нельзя менять выполненный/частичный шаг. Предложить новый порядок и подтвердить; все UUID/отметки сохраняются.
5. Пока шаг не завершён, complete отклоняется сервером. После 100% A предлагает finish, только B принимает. Ровно +50 Together XP, поздравление/дата, цель read-only. Reload/повтор HTTP не начисляет второй раз.
6. В другой активной цели A предлагает pause, B принимает; отметки запрещены. B предлагает resume, A принимает; отметки снова доступны. Предложить close, принять — окончательно closed. Любое ожидающее предложение можно отклонить или автору отозвать.
7. Проверить темы, узкий экран, клавиатуру, offline/online, безопасную ошибку и историю основных событий/согласий. Не показывать успешный бонус при неуспешном RPC.
8. Только если разрешено разорвать эту staging-пару: leave закрывает незавершённые цели и void pending, не отнимает XP/Coins/старый Together XP. Возвращение прежнего партнёра не открывает цель, новый не видит старую приватную историю; общий итог XP остаётся у пространства.
9. Direct INSERT/UPDATE/DELETE статусов, назначений, отметок, events/ledger и progress запрещены. Третья пара не читает/меняет цели по известным UUID. Для гонок использовать disposable DB-тесты, не правку облачных данных.

## Заключительное review: неизвестный результат запроса

Создание и предложение сохраняют одним intent исходные UUID, полный payload и счётчик собственных целей в пространстве (`p_expected_goals`) либо собственных согласований цели (`p_expected_changes`, включая activation и уже решённые). UUID не меняется при ошибке. Счётчик не обновляется при retry. Сервер под общей блокировкой сначала возвращает совпадающий same-key результат, включая терминальный, затем проверяет fence перед новым действием. Оба параметра имеют default 0; для следующего нового действия нужен актуальный счётчик. Подмена UUID со старого снимка завершается `goal_history_changed`, а не новым объектом.

Intent хранится в sessionStorage отдельно для пользователя и scope, с memory fallback при запрете storage. После reload доступна отдельная кнопка «Проверить прежний запрос»: `inspect_goal_request` только читает собственный результат, никогда не создаёт предложение. Если результат не найден, пользователь отдельно выбирает повторную отправку исходного intent. Начать новое действие можно отдельной кнопкой после обновления истории; она только очищает intent, а не отправляет новое предложение. Известный дубликат цели или шага требует дополнительного подтверждения создания отдельного объекта. Offline-запрос отклоняется немедленно; мутации не ставятся в очередь и не отправляются автоматически при reconnect.

Ограничения: после одновременной потери storage и памяти исходный UUID восстановить невозможно. Серверный fence защищает старый снимок, но не запрещает намеренно создать отдельную одинаковую цель с актуальными данными и явным подтверждением. Изоляция вкладок проверяется независимыми экземплярами модулей/storage и реальными конкурентными транзакциями; полноценный browser E2E двух окон не выполнялся.

## Журнал и read-only сверка

Клиентские INSERT/UPDATE/DELETE/TRUNCATE журнала уже запрещены grants/RLS; обход этих прав review не обнаружил. Дополнительный private trigger `protect_goal_reward` запрещает UPDATE и DELETE существующей награды даже обычным owner SQL. Исключение — каскадное удаление после удаления родительской цели для административной очистки disposable Auth fixtures. Это не защита от superuser, TRUNCATE владельцем или отключения trigger; пользовательского удаления аккаунта в MVP нет.

`supabase/tests/together-xp-audit.sql` — только read-only owner diagnostic: сравнивает space_progress с суммой task Together XP и goal ledger. Не предоставляет клиентского RPC и не исправляет историю. Историческое расхождение, в том числе после административного удаления, требует отдельного расследования. Глобальный reconciliation-trigger намеренно не добавлен: он блокировал бы штатные начисления при старом расхождении. Тесты подтверждают +50 за цель вместе с +20 за совместное задание, сохранение старого расхождения без переписывания, запрет изменения журнала, гонку двух подтверждений/task/leave и полный rollback, включая COMMIT-time ошибку.

В review: 85 UI/unit и 81 PostgreSQL-тест (75 security/RPC + 6 полных store migration), typecheck, lint и production build прошли. Локальный Supabase smoke прошёл на настоящих PostgreSQL/Auth/PostgREST с собственными временными аккаунтами. Сохраняется предупреждение Vite о большом JS chunk (~756 kB до gzip); разделение bundle — отдельная оптимизация.
