# Магазин добровольных наград — этап 4

## Продукт и согласия

Coins — исключительно игровые очки, не деньги. Нет платежей, вывода, переводов партнёру, долгов, штрафов, арбитража или принудительного исполнения. Списание не передаёт Coins исполнителю. XP и Together XP магазин не меняет. Создатель предлагает ритуал, который готов предоставить, а покупка приглашает договориться об актуальном согласии.

- **От партнёра:** автор — исполнитель, создание фиксирует его согласие и публикует награду. Купить может только второй участник.
- **Совместная:** автор согласен, второй участник принимает или отклоняет предложение. Только после принятия оно становится активным; купить может любой из двух, исключительно за собственные Coins. Второй стороной операции (технический provider_id) сервер назначает другого партнёра независимо от автора каталога. Это не единственный исполнитель: в событии участвуют оба. Платит и подтверждает получение покупатель; готовность или отказ подтверждает второй участник. Обе стороны могут отказаться до получения. В UI совместная покупка использует подпись «Второй участник», а не единоличный исполнитель.
- Для создания/покупки нужны два активных участника. Solo-пользователь продолжает зарабатывать и сохраняет Coins, магазин показывает ожидание.
- Название 2–100 символов после trim, описание до 1000, цена **1–100 000**, целое число. Категории: забота, романтика, отдых, развлечения, совместное время, другое. Шесть встроенных эмодзи, без файлов и внешних URL.
- Каталог создают пользователи; обязательных шаблонов нет. Редактирование цены/названия не реализовано: автор может снять предложение и создать новое. Совместное согласие не переносится на новую награду.

Состояния предложения: `pending → active | declined`, автор переключает `active ↔ paused`. `closed` после выхода — терминальное состояние; повторное вступление не открывает старые предложения. Исторические consent-строки сохраняются, терминальный статус предложения имеет приоритет.

## Покупка и исполнение

`pending → ready → completed`:

1. Покупатель отдельно подтверждает цену. Сервер проверяет согласия, членство, актуальную цену и баланс, создаёт покупку со snapshot, списание и обновляет баланс одной транзакцией.
2. Исполнитель может подтвердить готовность (`ready`) или отказаться. Готовность **не** завершает покупку.
3. Только покупатель после фактического получения нажимает «Я получил(а) награду» (`completed`). Действие окончательно; автоматического подтверждения/таймаута нет.
4. Пока покупка `pending` или `ready`, покупатель может отменить, исполнитель — отказаться. Оба действия переводят её в `cancelled` с полным однократным возвратом.

Если договориться не удалось, можно безопасно отменить. Пока покупатель не подтвердил получение, покупка остаётся открытой. Нет задолженности и штрафа за ожидание. Чата/расписания/медиации в MVP нет: время обсуждают лично. Снятие предложения с публикации не отменяет уже созданные покупки и не меняет правила возврата.

**Однократная** награда продаётся один раз за всю жизнь предложения, включая отменённую покупку: после возврата она не открывается повторно. Для новой попытки — новое добровольное предложение. **Многократная** допускает независимые повторные покупки с разными request UUID.

## Схема и история Coins

Новая миграция: `20261019220000_rewards_store.sql`, после всех трёх миграций PR #3.

| Таблица | Назначение |
|---|---|
| reward_offers | Неизменяемые поля каталога, два фиксированных участника, статус, request UUID |
| reward_offer_consents | Собственное согласие автора/адресата, время решения |
| reward_purchases | Покупатель/исполнитель с сервера, snapshot названия/описания/эмодзи/цены/типа/однократности, жизненный цикл |
| coin_transactions | Неизменяемые положительные amount с kind earn/spend/refund; владелец, ссылка на reward_ledger или purchase |

`reward_ledger` PR #3 остаётся неизменяемым положительным журналом XP/Coins/Together XP. Отрицательных записей туда нет. При миграции личные исторические начисления зеркалируются в `coin_transactions(kind=earn)` **без изменения balances**. Нулевые исторические факты сохраняются в reward_ledger без нулевых coin_transactions; обычные ограничения PR #3 по-прежнему запрещают нулевые личные начисления, а Together XP с coins=0 не зеркалируется. Новый пользователь без прогресса и без начислений допустим. Триггер на новые личные строки `reward_ledger` добавляет одно earn в той же транзакции исходного начисления; общий XP не создаёт Coins. UNIQUE reward_ledger_id исключает двойное зеркало.

`user_progress.coins = SUM(earn.amount) − SUM(spend.amount) + SUM(refund.amount)`.

Начисления из старого журнала нельзя дополнительно суммировать с earn нового: это ссылки на одни события. Исторический backfill проверяется до включения магазина; если старый баланс расходится с начислениями либо у владельца положительных начислений отсутствует строка progress, миграция останавливается с `coin_history_mismatch`, не исправляя/сбрасывая пользовательские данные. Она блокирует запись `reward_ledger` и `user_progress` на время backfill, поэтому требует отдельного согласованного окна применения. Не запускать из frontend или автоматически при setup.

История операций содержит положительные суммы, знак определяется kind. `get_coin_summary()` возвращает собственный balance и серверные earned/spent/refunded. Lifetime totals возвращаются десятичными **строками**, чтобы не округлять значения выше JS safe integer. Текущий balance остаётся безопасным целым 0…2^53−1. Потрачено/возвращено — валовые исторические суммы, отменённая покупка входит в обе.

Для гарантии возврата действует `coins + SUM(цен открытых покупок пользователя) ≤ 2^53−1`. Триггер на progress резервирует запас до предела: новые заработки не могут сделать обязательный возврат невозможным. При превышении откатывается всё начисление; это технический числовой лимит, не штраф. Изменения действующих reward rules/сумм наград PR #3 не потребовались.

## RPC и доступ

| RPC | Кто и что передаёт |
|---|---|
| create_reward_offer | Поля предложения и request UUID; партнёр/исполнитель определяются сервером |
| respond_reward_offer | Только адресат совместной награды: offer UUID и accept boolean |
| set_reward_offer_published | Только автор согласованной награды: offer UUID и published boolean |
| buy_reward_offer | Offer UUID + request UUID + p_expected_purchases (число показанных собственных покупок этой награды); никаких payer_id, цены, баланса или суммы |
| act_reward_purchase | Purchase UUID + ready/refuse (исполнитель), cancel/confirm (покупатель) |
| get_coin_summary | Без параметров, собственная сводка |
| can_read_reward_offer | Caller-scoped boolean для RLS |

RLS включена на всех четырёх таблицах. Authenticated имеет только SELECT; INSERT/UPDATE/DELETE через клиент запрещены, даже на собственных согласиях и журнале. Каталог/согласия видят только два исходных участника при текущем членстве. Покупки видят только их buyer/provider при текущем членстве. Собственный журнал Coins остаётся доступен после выхода, без названий чужих наград и идентификаторов других пользователей. Новому партнёру не открываются старые приватные предложения/покупки. Значимые RPC проверяют require_verified_user()/auth.uid(); все функции имеют фиксированный пустой search_path. PUBLIC/anon EXECUTE отозван, authenticated выдан только на перечисленные публичные функции. Внутренние record_coin_earning, check_coin_refund_capacity, refund_reward_purchase, close_rewards_on_departure недоступны клиентским ролям. Проверка — `supabase/tests/store-privileges.sql`.

Обычный пользователь не удаляет историю. Административное удаление аккаунтов с каскадами остаётся отдельной будущей retention-процедурой, как в PR #3; не является функцией этого этапа.

## Транзакции, идемпотентность и блокировки

Порядок: advisory user → space row → offer row → purchase row → progress row. Начисления задач идут user → space → task → instance → progress; операции членства user → space. Возврат другому человеку **не** захватывает его advisory user lock после space, иначе возник бы цикл с его leave/earn. Все операции под одним space сериализованы, независимо от разных HTTP-запросов; progress UPDATE дополнительно блокирует строку.

- UNIQUE(creator_id,request_id) для создания с проверкой идентичного payload.
- UNIQUE(buyer_id,request_id) для покупки: повтор того же offer возвращает прежнюю покупку даже после паузы/отмены, новый offer с тем же ключом отклоняется. После потери текущего членства старый ключ не восстанавливает доступ.
- Частичный UNIQUE(offer_id) WHERE single_use не допускает две продажи однократной награды.
- UNIQUE(purchase_id,kind) даёт ровно одно spend/refund, а терминальный статус исключает второй возврат. Завершение и отмена не могут победить одновременно.
- Проверки баланса выполняются на сервере под блокировками; при любой ошибке покупка/факт/списание/возврат/баланс откатываются вместе.
- В UI нет optimistic balance. Потерянный ответ повторяется с тем же ключом; незавершённый intent (UUID и исходный counter) атомарно хранится одним JSON в sessionStorage под user+offer (это не credential) и в памяти при недоступном storage. Retry не заменяет counter свежим, в том числе после перезагрузки: отклонённый запрос не должен превратиться в новое списание. Старый UUID без counter использует консервативный 0 и при устаревшей истории требует нового подтверждения. Пока успех не подтверждён, закрытие/открытие экрана сохраняет ключ. При потере sessionStorage и памяти UUID может быть утрачен, а разные вкладки могут иметь разные UUID. Поэтому сервер под теми же блокировками сравнивает p_expected_purchases с текущим количеством собственных покупок этой награды до нового списания. Устаревший экран с новым UUID получает reward_purchase_changed без списания, даже если предыдущая покупка уже завершена или отменена. После такого определённого отказа UI сбрасывает старый intent, обновляет историю и требует нового подтверждения. При неизвестном сетевом результате intent сохраняется. После перезагрузки с уже известной покупкой кнопка «Купить ещё» и подтверждение явно предупреждают об отдельном новом списании. Повтор прежнего UUID всегда возвращает прежнюю покупку до проверки counter. Для намеренной новой покупки свежий counter разрешён: это защита от устаревшего намерения, не ограничение количества покупок и не источник полномочий. Если сама предыдущая операция ещё выполняется, две разные отправки с одним counter всё равно сериализуются и только одна списывает Coins.

## Выход из пары

Триггер в транзакции leave закрывает предложения пространства, связанные с ушедшим, и отменяет все их pending/ready покупки с однократным возвратом **покупателю**, кем бы ни был инициатор выхода. Completed не отменяются. История не удаляется, XP/Together XP не меняются. Гонка purchase/leave приводит либо к отклонённой покупке, либо к созданной и тут же отменённой с возвратом. Гонка confirm/leave сохраняет завершённую покупку, только если confirm первым зафиксировал completed. Повторное вступление не воскрешает предложения, согласия на новые награды нужны заново.

## Интерфейс и ограничения MVP

Mobile-first, обе темы, пять разделов и Auth сохранены. «Награды»: собственный баланс, карточки/стоимость/автор/доступность, входящие согласия, фильтры Все/От партнёра/Совместные/Мои предложения/История; там же управление публикацией. История показывает собственные серверные суммы, покупки обеих сторон и последние 50 coin-операций. История после выхода показывает собственный accounting, приватные покупки скрыты. Демо содержит лишь явно обозначенные примеры с отключёнными покупками.

Клиент загружает разрешённые offers/consents/purchases offset-страницами по 200, UI выдаёт по 20. Как у задач, независимые HTTP-запросы не имеют общего snapshot; при конкурентных изменениях возможны временные пропуски/повторы. API max_rows должен быть ≥200. Polling 15 секунд + invalidation после действий дают eventual consistency, SQL всегда повторно проверяет баланс/согласие. Для больших объёмов нужен отдельный серверный keyset feed с RLS, bounded limit и actor-bound cursor по плану [tasks-economy.md](tasks-economy.md#ограничение-клиентской-пагинации-и-следующий-этап). Нет редактирования опубликованных полей, файлов, уведомлений, расписания, автозавершения, автоматических штрафов или автоматического повторного выставления однократной покупки.

## Применение миграции и проверки

Только после отдельного разрешения владельца на нужную тестовую среду, по [supabase.md](supabase.md). Порядок: `20261019150000_auth_profiles_couples.sql` → `20261019170000_tasks_economy.sql` → `20261019190000_tasks_security_review.sql` → `20261019220000_rewards_store.sql`. Никакого reset или повторной регистрации существующих пользователей. Новых env/Dashboard-настроек нет. Текущие `.env.example` и Auth redirect URLs сохраняются. Обновление типов — по прежней инструкции; snapshot клиента включает новые таблицы/публичные RPC, Insert/Update новых таблиц намеренно never.

`npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. `npm test` запускает UI и disposable PostgreSQL, применяет все миграции, проверяет historical backfill и сохраняет регрессии PR #2/#3. DB-тесты проверяют ограниченный баланс, earning/spending и single-use гонки, duplicate requests, snapshot, consent, cancel/confirm/unpublish/leave races, rollback на поздней ошибке, неизменяемость журналов, точные grants, изоляцию пар и refund headroom. `npm run test:supabase -- <LOCAL_STATUS_JSON>` дополнительно проверяет настоящий GoTrue/JWT/PostgREST с собственными новыми временными локальными аккаунтами. Не подключать тестовый runner к облачным пользователям.

### Ручной сценарий двух аккаунтов

Использовать только специально разрешённые staging-аккаунты; это checklist, не разрешение применить миграцию или изменить существующую пару.

1. A и B в одной паре. Оба выполняют свои обычные задания, записывают XP/Coins/Together XP. Проверить, что после миграции старые Coins не удвоились.
2. A создаёт «Выбор фильма», 5 Coins, многократную от себя. B видит A исполнителем; A не может купить собственную. Цена 0/дробная/выше100000 отклоняется.
3. A предлагает совместную «Прогулку». До согласия B купить нельзя. B сначала отклоняет без штрафов; для нового предложения принимает. Принять за B нельзя.
4. B подтверждает покупку при достаточном балансе: −5 Coins только у B, XP/Together XP прежние. Повторный HTTP с тем же request UUID не списывает снова. При недостатке сервер отклоняет. Две вкладки не могут создать отрицательный баланс.
5. A подтверждает готовность: покупка ещё не completed. Только B подтверждает фактическое получение. У completed нет отмены/возврата.
6. Новую покупку A отклоняет: B получает +5 один раз. Ещё одну B отменяет до получения с тем же результатом. Повтор кнопки/HTTP не удваивает возврат.
7. Однократную совместную купить одновременно из двух браузеров: только одна продажа, даже после отмены повторная продажа закрыта. Многократную купить снова с новым ключом.
8. A снимает каталог с публикации; новые покупки запрещены, история и возвраты прежних доступны. Reload и offline/online не создают фиктивного успеха. Проверить узкий экран, обе темы и клавиатуру.
9. Только на disposable/staging-паре, которую разрешено разрывать: выход любой стороны возвращает незавершённые покупки обоим соответствующим покупателям; completed и XP не меняются. Повторное вступление не открывает старый каталог, новый партнёр не видит чужую историю.
10. Прямой UPDATE balance/цены/согласия/покупки, INSERT/DELETE journal и внутренние RPC из authenticated/anon должны отклоняться; третья пара не видит операции. Заработано − потрачено + возвращено совпадает с балансом.


## Заключительное review PR #4

Проверки потери ответа охватывают same-UUID replay, разные вкладки/UUID с одним counter, потерю storage, перезагрузку модуля, неизвестный сетевой результат, исчерпанный баланс и уже проданную однократную награду. Проверка прежнего запроса доступна даже без Coins для новой покупки. При обновлении истории retry сохраняет исходный counter, не превращаясь в новое списание.

`supabase/tests/store-migration.mjs` исполняет **полный** SQL-файл на отдельных новых PostgreSQL-базах внутри disposable контейнера: успешный backfill; положительные факты без progress; нулевые legacy-факты и balances; нормальный Together XP с нулевыми Coins; mismatch; искусственную ошибку после backfill перед COMMIT. При ошибке откатываются новые таблицы, триггеры и grants, старые balances/ledger не меняются. Bootstrap этих тестов не применяется к Supabase.

Возвращение того же партнёра восстанавливает доступ к его собственной исторической операции в пространстве, но не меняет closed/cancelled и не разрешает повторное исполнение/публикацию. Другой партнёр не получает старые offers/consents/purchases и не может действовать по известным UUID. Earn/spend, два spend разных предложений, cancel/refund, leave/refund, unpublish/buy и COMMIT rollback продолжают проверяться реальным PostgreSQL.

Исправлен исходный **неприменённый удалённо** файл `20261019220000_rewards_store.sql`; требуется применить его финальную версию после трёх миграций PR #3. Для старого локального stack со старой сигнатурой нужен новый disposable stack. Не перезапускать CREATE TABLE миграцию поверх существующих данных и не сбрасывать удалённую базу. Если кто-либо уже применил раннюю версию к отдельному проекту, сначала нужна отдельно согласованная forward-миграция; этот review не даёт разрешения менять такую базу.
