# «Між нами» — спільна колода

150 авторських українських запитань, п’ять категорій по 30, постійні ID та версія 1. JSON-каталог — редагований вихідний файл; SQL seed у єдиній новій pending-міграції зберігає його точну копію. `npm run check:connection-catalog` перевіряє тотожність, кількість і унікальність. Каталог не генерується під час гри. Нові редакції після розгортання — окремі міграції та нові ID, без зміни історії. Статичні питання не є секретами: весь каталог входить у bundle, але закриті категорії не показуються у грі. Жодні відповіді не входять у bundle.

## Спільна механіка

Одна незавершена гра на простір. Запрошення → явне прийняття → серверна перестановка **всіх 150** ID один раз. `connection_deck` приватна серверна таблиця з unique `(session_id,position)` та `(session_id,card_id)`. Ні порядок, ні індекс наступного питання не читаються і не задаються клієнтом. Сесія зберігає номер поточної витягнутої карти; `connection_draws` — єдиний журнал витягувань. Активна карта визначається цією парою значень, тому паралельних активних карт немає.

`draw` приймає **очікуваний поточний номер**, не бажаний наступний ID. Сервер під user → space → session locks перевіряє статус і завершення участі обома, бере першу ще не витягнуту дозволену карту та збільшує номер рівно на один. Два різні request UUID з однаковим очікуваним номером не дають дві карти: один успіх, один `connection_changed`. Той самий UUID/intent повертає лише первісний результат, навіть після подальших переходів. Перезавантаження відновлює активну карту й власний чернетковий текст із БД.

## Комфорт і відверті категорії

«Високі температури» та «Таємне та бажане» потребують добровільного включення **обома**. Вимкнені карти залишаються у перестановці, не споживаються і не показуються; сервер обирає наступну дозволену. Після 90 базових карт може залишитися 60 закритих. Тоді можна завершити участь без тиску або окремо дозволити категорії обом. Екран «150 запитань…» показується лише після фактичного проходження всіх 150, а не після закриття часткової гри. Вимкнення категорій маскує також їх історію та чужі опубліковані відповіді; власні відповіді лишаються власнику через RLS. Поточне закрите запитання можна пропустити, не відкриваючи його.

Кожен може пропустити питання без пояснень; пропуск завершує лише власну участь. Пауза/відновлення доступні обом. Кожен може закрити гру самостійно. Жодна відповідь, вибір категорії або флірт не є згодою на фізичну дію. Немає таймерів, штрафів, streak чи нагород.

## Відповіді

`connection_answers` відокремлює draft, submitted, published, skipped і version. Чернетка до 2000 символів доступна тільки автору. Надсилання потребує окремого прапорця публікації; до двох завершених участей чужий текст не розкривається ні RPC, ні RLS. Пропуск не містить тексту. Сервер визначає автора з `auth.uid()`, не приймає чужий user_id. Version CAS не дає другій вкладці перезаписати вже надісланий текст.

Після обох відповідей/пропусків можна йти далі. Історія лишається в попередній грі; нова сесія створює нову перестановку. Видалення власних відповідей усієї гри — окрема явна кнопка, яка закриває гру та відкликає спільний перегляд. Вона не видаляє власний текст партнера. Після виходу shared-доступ припиняється назавжди для старих membership ID, навіть при поверненні того ж партнера; новий партнер не бачить назв, UUID, дат, лічильників чи змісту старих сесій.

`notify` створює одне внутрішнє запрошення на `(session,slot,sender)`, без відповіді чи публічного URL; не витягує карту. Індикатор веде саме на запрошену карту (`?card=N`), навіть якщо гра вже пішла далі. `ack` відзначає лише власні повідомлення одержувача. Історія — bounded server keyset, 20 карт на сторінку. Це live keyset, не MVCC snapshot.

## Невідомий результат

UI зберігає початкові request UUID, expected version та payload разом у sessionStorage користувача; коли storage недоступне — в пам’яті компонента. Чернетка на сервері — основне довготривале збереження. При timeout немає автоматичного retry, offline queue чи нового UUID. Доступна SELECT-only перевірка `connection_read('request')` та явний повтор того самого intent. Для відмови від невідомого запиту є окрема кнопка; перед новою дією слід перевірити історію. При повній втраті browser storage серверні creation counters, unique live-session та CAS переходів залишаються останнім бар’єром проти дублікатів. Нове запрошення після завершення попередньої сесії — нова явна дія.

Journal зберігає лише SHA-256 канонічного intent та нечутливий результат (UUID/порожній object), **не** тексти. Успішні intents прибираються з sessionStorage; видалення відповідей чистить локальні intents цієї сесії. SessionStorage — локальні дані довіреного браузера, не гарантія проти локального доступу до пристрою. Немає зовнішніх AI, аналітики відповідей чи логування текстів. Клієнтський cache прив’язаний до user + membership epoch; помилка доступу не показує старий cached shared report. Авторизовані раніше копії/скриншоти не можна дистанційно відкликати.

## SQL і розгортання

Єдина pending-міграція: **`supabase/migrations/20261022120000_emotional_connection.sql`**, після `20261021120000_couple_rituals.sql`. Старі міграції не змінюються.

Таблиці: `connection_catalog`, `connection_moods`, `connection_reactions`, `connection_sessions`, `connection_answers`, `connection_deck`, `connection_draws`, `connection_events`, `connection_requests`. RLS на всіх, жодних прямих клієнтських записів. Deck/draw/request journal без клієнтського SELECT.

Публічні RPC: `connection_action(text,uuid,integer,jsonb,uuid)` та `connection_read(text,uuid,jsonb)` — verified Auth, SECURITY DEFINER, порожній search_path. RLS-предикати `connection_access`, `connection_mood_access`, `connection_answer_access` — authenticated-only, лише boolean. Приватні `connection_clock`, trigger `connection_departure` недоступні anon/authenticated. `supabase/tests/connection-privileges.sql` перевіряє точні effective ACL, RLS і search_path також на справжньому Supabase.

Усі часи/авторство/переходи визначає сервер. Leave-trigger закриває незавершені сесії й прибирає mood-sharing, не зачіпає економіку. Додавання не пише в жодний наявний XP/Coins/Together XP журнал.

Безпечний порядок: review SQL → резервна копія/окрема staging-середа → стандартні попередні міграції → нова міграція однією транзакцією → reload PostgREST schema cache → audit grants/RLS та smoke на **нових staging акаунтах** → frontend. Застосування до remote потребує окремого дозволу. Нових env/secrets або Dashboard-провайдерів не потрібно; чинні `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY` та Auth redirect settings залишаються.

## Візуальна частина й перевірки

Карта 2:3, п’ять відтінків, окремі символи/назви, декоративна рамка, рубашка, перспектива, flip по click/native keyboard, м’які draw/answer/completion анімації. Hover не запускає мутацію. `prefers-reduced-motion` вимикає рух. Системні шрифти із підтримкою української; жодних важких зображень/зовнішніх шрифтів.

Команди: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`; `npm run test:supabase -- /tmp/OWN-local-status.json`; `npm run test:connection-browser` на readonly loopback DEMO preview. Додатково `npm run test:connection-accounts -- /tmp/OWN-local-status.json http://127.0.0.1:4174` на loopback build із локальною Supabase-конфігурацією: два нові видалювані Auth акаунти, два ізольовані Chromium profiles, спільна карта, приватна чернетка, сліпа публікація та конкурентний перехід. Ніколи не передавати cloud status/URL чи існуючі облікові записи.

Обмеження: polling 10 секунд, не realtime; немає push/email; немає клінічних висновків, native SDK або нагород; жодної гарантії strict snapshot. Повний mobile/desktop visual QA на фізичних пристроях залишається наступним ручним кроком. Окремого UI експорту архіву після розриву немає: авторський read/delete RPC доступ збережений, спільна історія закрита.

## Перевірений результат цього етапу

- Typecheck, lint (без попереджень), production build — успіх.
- `npm test`: 128 UI/unit + 122 реальних PostgreSQL перевірки (116 security/RPC, 6 повних міграційних), без пропусків; усі попередні suites збережено.
- Локальний Supabase: PostgreSQL 17.11, GoTrue 2.197, PostgREST 16.4; справжні email/PKCE/recovery/Auth/JWT/RLS/RPC, економіка попередніх етапів, відгук доступу та cleanup власних локальних користувачів — успіх.
- Два ізольовані Chromium profiles з новими локальними Auth акаунтами: UI запрошення/прийняття, одна карта, збережена приватна чернетка, прихована перша публікація, пропуск, спільний перегляд, одночасний перехід та reload — успіх. Обидва акаунти видалені.
- Chromium readonly demo: 360/390/768/1280 px × дві теми, keyboard/click flip, reduced motion, перенос тексту, п’ять вкладок, без горизонтального скролу — успіх. Скриншот перевірено візуально.
- Окремі регресії: 150 витягувань без повторів і нова колода; одночасні підтвердження опитування; реальне очікування PostgreSQL lock через UTC-північ; COMMIT-time rollback; інтимна категорія після відкликання згоди; два shared mood при видаленні одного локального Auth акаунта.

CLI health-check локального Auth може показувати `unhealthy` у цій cloud sandbox, проте прямий `/auth/v1/health` повернув 200 та всі наведені реальні SDK/browser сценарії пройшли. Не прирівнюємо один статус CLI до перевірки функціональності. Build зберігає попереднє попередження про великий JS chunk (~877 kB minified / ~243 kB gzip); це не помилка збірки, розділення bundle лишається оптимізацією наступного етапу.

Видалення Auth акаунта каскадно видаляє спільні сесії цього акаунта разом з відповідями; mood іншого власника зберігається приватним із nullable посиланням на колишнє членство. Звичайний вихід із простору **не** видаляє авторські факти.
