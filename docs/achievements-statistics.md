# Достижения, статистика и совместный путь — этап 6

## Экран и модель

Раздел `/us` сохраняет управление парой, приглашения, профиль и самостоятельный выход. Добавлены общий прогресс, личные и совместные показатели, достижения, календарь и история. Шестой вкладки нет. Светлая/тёмная темы, mobile-first карточки, доступные progress, текстовые значения графика, skeleton, empty/error/retry и reduced motion используют существующую дизайн-систему.

Достижения **вычисляются сервером**, не начисляют очки, не являются отдельной наградой или клиентским состоянием. Повторный запрос не открывает вторую копию. Исторические факты учитываются сразу; миграция не переписывает журналы и балансы. Индивидуальные пороги относятся к собственным выполнениям заданий, включая свою часть совместного задания; полное совместное выполнение считается отдельно один раз на экземпляр. Разные daily/weekly экземпляры — разные действия.

## Источники истины

| Метрика | Источник и ограничения |
|---|---|
| Личные XP / текущие Coins | Собственная строка `user_progress`; отсутствие строки = 0. Coins — остаток после покупок/возвратов, не заработанная сумма |
| Собственные выполнения / personal badges / активность | `reward_ledger.kind='personal' AND user_id=auth.uid()`. UNIQUE completion_id и (instance_id,user_id) не дают удвоить HTTP-повтор. FK указывает на реальный task_completions; его не считаем второй раз |
| Совместные задания | Одна `reward_ledger.kind='together'` на полностью выполненный joint instance; две personal строки не увеличивают общий счётчик |
| Достигнутые цели | Одна `goal_reward_ledger` на goal_id, только после взаимного завершения. Предложения, шаги и goal_events не являются дополнительными достигнутыми целями |
| Вместе XP | Текущий `space_progress.together_xp`, исторический итог пространства |
| Завершённая награда в истории | `reward_purchases.status='completed' AND resolved_at IS NOT NULL`: готовность исполнителя и подтверждение покупателя прошли существующий RPC. Pending/ready/cancelled/refund не считаются получением |
| Даты | Серверные `reward_ledger.created_at`, `goal_reward_ledger.created_at`, `reward_purchases.resolved_at`. Дата достижения = дата N-го подходящего факта |
| График XP | Доступные task Together + goal факты; cumulative включает доступные начисления до начала 30-дневного окна. Показывается только при точном равенстве их суммы общему итогу |

`task_completions` и `goal_events` остаются первичными деталями предметных объектов. Их нельзя суммировать вместе с reward ledgers: один бизнес-процесс создаёт несколько строк. Этап 6 не меняет +20 за joint task, +50 за goal, личные XP/Coins и правила магазина. Расхождения истории не исправляются автоматически; owner-only read-only audit из этапа 5 остаётся диагностикой.

## Приватность и состав

Личные счётчики, даты и серии относятся **только к вызывающему пользователю**, включая его сохранённую личную earned историю после выхода. Другому партнёру нет ни имени личного задания, ни дат, ни счётчиков личной активности. Сравнения партнёров нет.

Общие действия и badges joint/goal относятся к **доступной истории нынешних двух участников**, включая прежние периоды участия этих же людей. Помимо `can_read_task`/`can_read_goal`, оба исходных участника должны сейчас состоять в том же пространстве. Для покупок фиксированные buyer/provider должны совпадать с текущим составом. Поэтому оставшийся участник не видит в новом общем feed события прежней пары; новый партнёр не получает старые названия, даты, object UUID или косвенные счётчики этой истории. Без второго участника эта часть пуста.

Together XP и его три памятных порога принадлежат пространству и сохраняются при смене состава. UI отдельно говорит, что это включает прежних участников и не является заслугой нынешней пары. Новый партнёр может видеть исторический **итог**, но не его скрытые даты. Если доступные начисления не объясняют итог, полный график скрыт с объяснением. Возвращение исходного партнёра возвращает доступ к истории, не открывает закрытые цели, не возобновляет покупки и не начисляет ничего.

Ключи TanStack Query содержат user id и epoch текущих membership UUID. Auth очищает cache; create/accept/leave явно сбрасывают статистику/feed. Изменения task/goal/store инвалидируют эти запросы. Внешняя смена членства обнаруживается существующим polling пары (до 15 секунд); сервер проверяет доступ при каждом запросе независимо от cache.

## UTC и активные дни

Календарь — 30 календарных дней **UTC**, включая сегодня. 7-дневный интервал = сегодня и предыдущие 6; 30-дневный = сегодня и предыдущие 29. Активный день — хотя бы одно собственное выполнение задания по личному reward fact. Открытие приложения, предложения, отклонения, покупки и повтор HTTP активностью не считаются. Шаги целей в этот показатель не входят; UI прямо называет его собственными выполнениями заданий.

Текущая серия оканчивается сегодня либо вчера, если сегодня ещё нет выполнения. Лучшая серия считается по всей сохранённой собственной истории. Пропуск не меняет XP/Coins и не создаёт штрафа/уведомления. Календарь выводит число собственных выполнений; график показывает накопленный Together XP с доступными текстовыми значениями.

## SQL и права

Новая pending migration: **`supabase/migrations/20261020120000_achievements_statistics.sql`**, после `20261020090000_couple_goals.sql`. Старые миграции не меняются.

- `statistics_joint_facts`: внутренний `security_invoker=true` view, без клиентских grants; явно проверяет caller и обоих действующих участников. Нормализует три независимых источника, не создавая бизнес-фактов.
- `get_statistics()` — verified caller, STABLE SECURITY DEFINER, фиксированный пустой search_path, bounded JSON (13 badges + 30 дней + агрегаты). Нельзя передать user_id, XP, счётчик или фильтр.
- `get_joint_history(jsonb,integer)` — verified caller, SECURITY DEFINER, только фиксированные источники и keyset; первая страница сохраняет технический snapshot session, последующие читают его. Не изменяет игру.
- `acknowledge_statistics()` — verified caller, SECURITY DEFINER, сервер сам вычисляет unlocked codes, сериализует запись own seen state под user → space lock. Не принимает клиентские codes/counters.
- Внутренние invoker helpers `statistics_context`, `statistics_badges`, `statistics_visible` не имеют EXECUTE для PUBLIC/anon/authenticated.
- `statistics_seen`: RLS, authenticated только SELECT своей строки, запись только RPC.
- `statistics_history_sessions`: RLS без клиентских policies/grants, включая SELECT. Хранит снимок, actor и membership epoch только на сервере.

Read-only проверка grants: `supabase/tests/statistics-privileges.sql`. Все public RPC запрещены anon/PUBLIC; прямые изменения защищённых данных запрещены authenticated. Ошибки cursor/SQL переводятся в безопасные сообщения без внутренних деталей.

## Пагинация и конкурентность

Feed сортируется `(at DESC,key DESC)`, key включает тип и уникальный UUID либо badge code. Клиент получает 20 событий, сервер разрешает limit 1–50, каждый source берёт максимум limit+1 кандидатов, achievement source — первые 25 joint/10 goal фактов. Offset и загрузки всей истории ради первой страницы нет.

Курсор `{session,at,key}` — непривилегированный указатель, не bearer token. Сервер сверяет owner, текущие membership UUID, срок и форму. Смена состава, даже выход/возвращение того же человека, инвалидирует прежний cursor. Ошибка предлагает начать историю заново. Внутренний `pg_snapshot` первой страницы не передаётся браузеру. Проверка xmin/видимости исключает поздние COMMIT с более ранним transaction timestamp: они не сдвигают пороговые даты и не дублируют achievement event в текущей прокрутке. Обновление с начала покажет новые факты.

Сессия живёт 30 минут, максимум 10 на пользователя; новая первая страница под advisory lock удаляет его просроченные/лишние сессии. Нет cron или глобального удаления. У неактивного пользователя может остаться до 10 просроченных технических строк до следующего просмотра/административной retention. Это не сохранённый PostgreSQL snapshot, не держит транзакцию/соединение и не мешает vacuum.

Курсоры рассчитаны на обычные неизменяемые business facts; superuser/административное переписывание или удаление фактов не поддерживает стабильную прокрутку. Клиент не может этого сделать. Нет realtime общей snapshot-транзакции между сводкой и feed: сводка может быть новее просматриваемой истории. Даты порогов вычисляемы, при refresh могут учесть ранее не зафиксированный факт.

## Поздравления

Первое acknowledge создаёт **молчаливую историческую baseline**, а не поздравляет за весь импорт. Последующие возвращают только новые серверно вычисленные codes, атомарно отмечая показ. Смена состава молча устанавливает новую общую baseline; личная baseline сохраняется. Reload, другое устройство и конкурентные acknowledge не повторяют поздравления. Клиент дополнительно подавляет повтор показа в том же runtime.

Гарантия показа — at-most-once, не гарантированная доставка: потерянный ответ после COMMIT может оставить новое достижение без всплывающего поздравления. Сам badge и история остаются доступны. Никаких игровых эффектов или начислений при acknowledge нет.

## Производительность и ограничения

Частичные индексы: own personal ledger по user/time, joint ledger и goal ledger по space/time/event key, completed purchases по space/resolved time/event key; membership и исходные PK/unique индексы сохраняются. Сводка читает только свою и доступную историю, повторно использует материализованный CTE общих фактов, возвращает агрегаты вместо строк истории. Клиентский cache 60 секунд, без периодического polling сводки; собственные изменения инвалидируют его.

EXPLAIN ANALYZE на disposable PostgreSQL 17, fixture **3 000 joint instances / 9 000 ledger rows**: глубокая source-page использует `statistics_joint_facts_idx`, ~0,7 мс; полная сводка ~35 мс в текущей среде. Первая страница может обоснованно использовать seq scan + top-N на небольшом fixture. Это наблюдение теста, не production SLA и не benchmark множества пользователей. Тест проверяет фактический план и строки, не отключает seqscan.

Полная сводка (lifetime counts, best streak, точные даты) остаётся O(доступной истории); при существенно больших объёмах нужен отдельный измеренный server aggregate cache/материализация с unique source keys и согласованным backfill. Его нельзя заменять доверенными клиентскими counters. Старые workspace-загрузчики tasks/store/goals всё ещё используют документированную offset-пагинацию; **новый feed** имеет самостоятельную серверную keyset-пагинацию. Ссылки на task instance и receipt открывают разрешённую read-only карточку по query parameter в существующих разделах; goal имеет собственную detail route.
