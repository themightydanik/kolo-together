## План и границы

Альбом — новая предметная сущность, не inbox. Черновик видит только автор. Явная публикация автора открывает текст и выбранные фото обоим текущим исходным membership. У каждого отдельная заметка, редактируемая только им. Автор может отозвать/удалить своё содержание; чужая заметка сохраняется как приватная карточка без прежних названия/даты/источника/фото. Отзыв окончательный: новая публикация — новый спогад, не восстановление чужих слов. После leave старый epoch закрывает весь альбом/файлы для обеих сторон, rejoin не восстанавливает историю. Это не новый личный архив после выхода.

Фото — private bucket `couple-memories`. Raw Storage read/sign/list/upload/delete для anon/authenticated запрещены restrictive policies, включая обход через широкую существующую policy. Edge Function `memory-files` проверяет реального пользователя и purpose-specific RPC перед service-side upload/download/cleanup. Это предотвращает выпуск клиентом произвольно долгих signed URLs. Получаем authenticated bytes, используем локальные Blob URL и освобождаем их при unmount/epoch/error/offline; ответ no-store. Уже полученные пользователем байты отозвать невозможно.

Upload двухфазный: случайный reserved path + SHA256/type/size → bounded/magic-checked server upload → ready manifest. Только явный Save прикрепляет до пяти photo IDs. До пяти дополнительных staging slots позволяют безопасно заменить пять старых фотографий; Cancel удаляет только новые staging, не сохранённые фото. Неполный upload не публикуется. Не удаляем файл при неизвестном результате finalize: retry проверяет ту же reservation; cleanup работает с явно отозванными или истёкшими slots. Технический cleanup можно повторять без новой публикации.

Новая migration, RLS, server UTC timestamps, user→space→memory locks, version CAS, request journal и opaque epoch/filter-bound keyset pagination. Никаких изменений XP/Coins/Together XP, новых уведомлений, paywall или лимита количества воспоминаний.

Источники выбираются из завершённых joint task/goal/ritual и shared achievement (не личных/исторического XP прежних составов). Проверяем текущий доступ и completion после начала обоих исходных membership; ссылку/название источника проецируем заново, не snapshot. Не копируем ответы, mood или автоматически названия источников в собственный текст. Уникальная связь source/membership защищает от дубликата, только по явному действию. При отзыве source связь исчезает, авторский рассказ остаётся отдельным текстом.

## Дані та контракти

Міграція: `supabase/migrations/20261025120000_couple_memories.sql`. Старі міграції не переписані. Таблиці `couple_memories`, `memory_notes`, `memory_photos`, `memory_requests`, `memory_cursors` мають RLS; клієнт не може писати в жодну. Сирі metadata спогаду/фото/receipts/cursors недоступні для SELECT. `memory_notes` дозволяє лише поточний дозволений власний або опублікований текст. Безпечні проєкції не повертають source UUID після втрати доступу.

Публічні authenticated RPC: `memory_action`, `memory_detail`, `memory_feed`, `memory_inspect`, `memory_file`, `memory_sources`; `memory_note_visible` — тільки boolean predicate для RLS. Кожна операція з даними перевіряє підтвердженого Auth user. Внутрішні `memory_epoch`, `memory_visible`, `memory_source`, `memory_lock` закриті для PUBLIC/anon/authenticated. `memory_prune_photo` і `memory_gc_candidates` доступні виключно service_role. Усі SECURITY DEFINER мають фіксований порожній search_path. Service key існує тільки на сервері.

Ідентичний request UUID прив'язаний до hash повного первісного action/id/version/payload. Replay повертає receipt, а не повторює мутацію; зміна payload з тим самим UUID відхиляється. CAS перевіряє memory version або незалежну версію власної нотатки. Creation fence — кількість створених автором записів, тому дві вкладки зі старою формою не створюють непомітні дублікати з різними UUID. За втрати sessionStorage цей fence та version продовжують захищати повтор, але локальний незбережений текст/Blob не відновлюється. UI не надсилає бізнес-мутації на reconnect: є окремі «перевірити результат» (SELECT-only) та повтор первісного наміру. Новий UUID — тільки нова явна дія. Upload має власну стабільну reservation UUID і digest; повтор не створює іншого об'єкта.

Сортування — event_date DESC, id DESC. Opaque cursor прив'язаний до actor, точного epoch, категорії та server ceiling; TTL 30 хв, RPC limit 1–40, UI сторінки по 20 і максимум 5 сторінок у пам'яті. Server ceiling відсікає нові та відредаговані записи до refresh. Це live keyset, **не MVCC snapshot**: пізній COMMIT може з'явитися лише на refresh, видалення/відкликання застосовуються відразу; редагування може прибрати рядок з поточної послідовності. Немає OFFSET або завантаження всієї історії в браузер. «Оновити» починає нову послідовність. Picker джерел навмисно показує лише до 40 останніх дозволених моментів (до 20 на тип), не весь архів.

## Фото, видалення й експлуатація

Вхід клієнта: JPEG/PNG/WebP до 10 MiB; canvas до 1920 px, JPEG quality .82, без EXIF, вихід до 5 MiB. Сервер обмежує streamed body до 5 MiB + 64 KiB multipart, перевіряє magic/type/size/SHA256 проти reservation; SVG/HTML не приймаються. Service upload не перезаписує шлях, а commit перевіряє Storage metadata. `memory_file` не дозволяє вибрати чужий bucket/path/owner. Список файлів не містить original filenames. No signed URLs; клієнт отримує лише authenticated bytes через `memory-files` з no-store.

«Прибрати фото» у редакторі не видаляє збережений файл до Save. Save атомарно перемикає manifest; старі файли відразу не читаються і переходять до cleanup. Cancel видаляє лише нові staging slots. Помилка cleanup не відновлює доступ і не стирає manifest до фізичного видалення. Невикористаний staging (reserved **або ready**) спливає через 15 хв; завершити редагування після expiry може знадобитися з повторним вибором фото. Збережені attached фото не мають TTL. Save блокує photo rows перед перевіркою, GC використовує SKIP LOCKED: файл не може бути одночасно прикріплений і вилучений як staging.

Withdraw фінальний: приховує авторську історію від партнера та всі фото, зберігає текст автора в БД і окремі нотатки. Delete очищує авторські title/story/source та закриває фото, але залишає tombstone/receipts для ідемпотентності й чужу нотатку. Власне видалення нотатки очищує body, зберігає її monotonic version. Новий партнер не бачить навіть tombstone. Вихід закриває epoch; серверна maintenance вилучає фото. Видалення Auth user каскадно видаляє записи початкової пари; Storage orphan після каскаду підбирає maintenance. Не обіцяємо відкликати вже завантажені/збережені користувачем байти.

Клієнт викликає безпечний cleanup при відкритті редактора/після змін. Для покинутих сесій потрібен **операторський серверний job**: `SUPABASE_URL` і `SUPABASE_SERVICE_ROLE_KEY` у secret environment → `node scripts/cleanup-memory-files.mjs`. Один запуск до 100 файлів; повторювати до порожнього batch, потім періодично. Job видаляє Storage object, тільки потім prune manifest; помилки повторювані. Ніякого cron/remote job цей PR не створює. Без job сироти можуть залишатися фізично, але недоступні клієнту. Узгодити retention/backups з оператором перед реальними фото. Тексти request journal не дублює: лише hash наміру й receipt.

5. Пройти два аккаунти: A створює draft/2 фото, B не бачить; A явно публікує; B додає власну нотатку; A редагує/скасовує заміну фото; A withdraw → B бачить лише власну нотатку, жодних авторських metadata/фото; leave/rejoin/new partner → старий album/cursor/file ID недоступний. З відомим шляхом перевірити raw Storage download/sign/list заборонені. Перевірити retry після offline/timeout без нового UUID.

## Відомі межі продукту

Без підписки, paywall, count limits або нової економіки. Майбутній freemium може доповнювати персоналізацію/формати, але не блокувати перегляд уже збережених спогадів після завершення Premium. Миттєвого відкликання вже отриманих байтів на іншому пристрої без мережі не існує.

## UX review: непомітне фонове оновлення

Підтверджений ручним тестом дефект PR #11: `hidden` залежав від `memory.isFetching`, а context `enabled` — від `couple.isFetching`. Звичайні успішні 10/15-секундні запити ховали форму й альбом; key нотатки з її server version також міг знищити локальний текст. Це не було відкликанням доступу.

Виправлено: polling і focus revalidation залишаються, але не змінюють видимість, focus, mounted editor або доступність кнопок. Initial loading — тільки без даних. Membership IDs/auth/error/epoch є межею доступу, `isFetching` — лише транспортний стан. Confirmed auth/access error, інший epoch, withdraw/delete прибирають приватний вміст і звільняють Blob URL; звичайний refetch цього не робить. Незмінний photo UUID позначає immutable bytes, тож зміни тексту/нотаток не запускають повторне завантаження фото.

Редактор тримає початковий CAS, RHF defaults, дату, категорію, згоду, локальні фото й upload job протягом усієї сесії редагування. Нову server version показує як конфлікт без автоматичної заміни чернетки. «Оновити збережені дані» потребує підтвердження відкидання локальної форми; лише ця явна дія змінює editor key та завершує старий save intent. Нотатка має стабільний key, окремий початковий CAS і явне завантаження серверного тексту. Успішний save/replay синхронізує note CAS з **первісним intent.expected**, не з потенційно новішим render. Серверні перевірки/CAS/RLS не змінені.

Міграцію `20261025120000_couple_memories.sql` користувач уже застосував: вона незмінна в цьому виправленні. Edge Function також не змінена; тестова SQL інсталяція виконується виключно на новому disposable local Supabase.

Регресії: unit перевіряє DOM identity/видимість/selection/фокус/усі поля під час fetch, note CAS проти іншої вкладки, context fetch проти справжнього auth/epoch error. Реальний Chromium/WebKit сценарій друкує понад 60 секунд зі staged фото й увімкненим polling, контролює кожен animation frame (CSS visibility, незмінний editor node, фото та focus), caret і значення полів, tab/focus return, partner note sync, іншу server version, withdraw/leave. Fake timers або моків Auth/RPC/Storage у цьому сценарії немає.
