# Добровольные ритуалы пары — этап 7

## Назначение и экраны

Ритуал — необязательное время вместе, отдельно от заданий и магазина. Никаких XP, Coins, Together XP, достижений за количество ритуалов, платежей или обещаний награды. Пропуск не означает неудачу и ничего не отнимает. Каждый может отказаться без разрешения другого.

«Сегодня» содержит блок **«Наши ритуалы»** с текущими экземплярами. В `/us#rituals` — создание, согласования, фильтры «Активные», «Ожидают согласования», «На паузе», «Завершённые», календарь и история. Основных вкладок остаётся пять; прежнее управление парой/приглашения/выход, задания, цели, магазин и статистика сохраняются.

Девять готовых идей только заполняют форму, не создают серверное предложение автоматически: утреннее пожелание; 10 минут без телефонов; три вещи, за которые мы благодарны; вечерний разговор; совместный кофе или чай; маленький сюрприз; прогулка вдвоём; объятия; обсуждение планов на завтра. Можно задать свои название (2–100 после trim), описание (до 1000), одну из девяти встроенных emoji и расписание. URL/HTML/загружаемые иконки отсутствуют. Вариант «Объятия» и общий текст прямо говорят: согласие на ритуал не подразумевает согласия на физический контакт в конкретный момент.

Без Supabase показывается только явно обозначенный read-only пример без сессии, согласий, отметок, балансов или сохранения фактов.

## Согласия и право отказаться

Два фиксированных равноправных участника, без администратора. Создание требует действующей пары. Предложивший уже согласен с собственным предложением; второй принимает или отклоняет. До принятия нет экземпляра и выполнить нечего. Автор может отозвать pending предложение.

`pending → active | declined | closed`. `active ↔ paused` и окончательное `active | paused → closed` — через новое предложение и решение второго человека. Изменение содержания/иконки/расписания — отдельное согласование `edit`. Есть только **одно pending согласование на ритуал**: пока оно ожидает решения, отметки и новые предложения заблокированы, чтобы условия не изменились после согласия одной стороны. Отклонение/отзыв изменения сохраняет прежний status и terms.

В дополнение к взаимному закрытию есть отдельная подтверждаемая команда **«Отказаться от дальнейшего участия»**. Её может выполнить любой из двух исходных текущих участников, в том числе при ожидающем согласовании. Она немедленно закрывает ритуал, void pending consent и останавливает незавершённые экземпляры, без разрешения партнёра. Подтверждённые отметки и завершённые экземпляры не удаляются. Closed/declined терминальны; возобновить их нельзя, в том числе после повторного вступления.

Редактирование и возобновление после принятия действуют **со следующего календарного дня UTC**. Принятое edit/pause/close переводит незавершённый экземпляр в missed с причиной изменения, сохраняя его отметки и старый снимок условий. Завершённый экземпляр не меняется. Нельзя закончить сегодняшнее участие по одним условиям, а второе — по другим.

## UTC и ленивые экземпляры

Расписания:

- `daily`: все ISO-дни 1–7.
- `weekdays`: выбранные уникальные ISO-дни 1–7 (понедельник — 1).
- `weekly`: ровно один выбранный ISO-день.

`refresh_ritual_instances()` вызывается при чтении первой страницы/«Сегодня» и создаёт **только текущий подходящий день UTC**. Cron не нужен. Дни, когда приложение не открывали, не восстанавливаются задним числом. Уже созданные незавершённые прошлые экземпляры получают `missed` при следующем refresh. Паузы/отказ/выход также останавливают текущие незавершённые экземпляры.

Daily/weekdays ключ `d:YYYY-MM-DD`; weekly — `w:YYYY-MM-DD` понедельника ISO-недели. UNIQUE(ritual_id,period_key) и UNIQUE(ritual_id,scheduled_on) не допускают дубля периода или даты. Weekly выполняется только в выбранный день, а не до конца недели. Смена выбранного weekly-дня не создаёт второй weekly instance той же недели. При смене **типа** расписания действуют ключи нового типа, но существующая конкретная дата не повторяется. Расписание считается по серверному времени после бизнес-блокировок; время/период не принимаются от клиента.

Экземпляр хранит `terms` и `version`: история показывает именно согласованные тогда условия. Его состояния:

| Сервер | Интерфейс |
|---|---|
| waiting | Ожидает |
| partial | Отметил один участник, ждём второго без спешки |
| completed | Выполнено вместе |
| missed | Этот день прошёл; отметки сохранены, штрафов нет |

Каждый передаёт только instance UUID; сервер берёт исполнителя из `auth.uid()`. PK(instance_id,user_id) и сериализация по пространству защищают две независимые отметки. Только две отметки одного экземпляра завершают его; разные дни/недели не объединяются. Повтор своей уже сохранённой отметки возвращается без записи, даже если период завершён/ритуал закрыт, пока доступ разрешён. Это не новая отметка за другой день.

## Схема и RPC

Новая pending migration: **`supabase/migrations/20261021120000_couple_rituals.sql`**, после `20261020120000_achievements_statistics.sql`. Старые миграции и экономика не меняются. Backfill или начисления отсутствуют.

- `couple_rituals`: два исходных участника, пространство, текущие валидированные terms/status/version/starts_on, create request UUID.
- `ritual_consents`: immutable payload предложения, author/request UUID, kind и решение. UNIQUE requester/request и один pending на ritual.
- `ritual_instances`: снимок условий, период/дата, состояния и причина остановки. Composite FK(ritual_id,space_id) гарантирует совпадение пространства, history index начинается с space_id.
- `ritual_completions`: собственные неизменяемые клиентом отметки, PK(instance,user).

На всех четырёх таблицах RLS; authenticated получает только SELECT разрешённых строк. INSERT/UPDATE/DELETE/TRUNCATE запрещены. Все записи только через verified-user RPC с пустым фиксированным search_path.

| Public RPC | Назначение |
|---|---|
| create_couple_ritual(request,terms,expected_creations) | Создать pending ритуал, без экземпляра |
| propose_ritual_change(ritual,request,kind,terms,expected_changes) | Новые условия / pause / resume / close |
| resolve_ritual_consent(consent,decision) | accept/decline только адресатом; withdraw только автором |
| withdraw_couple_ritual(ritual) | Односторонний отказ от дальнейшего участия |
| refresh_ritual_instances() | Материализация только сегодняшнего периода, возвращает UTC day |
| complete_ritual_instance(instance) | Одна собственная отметка |
| inspect_ritual_request(request,ritual?) | SELECT-only поиск собственного результата |
| list_couple_rituals(filter,cursor,limit) | Ограниченные страницы карточек, текущие consent/instance/marks и own request counters |
| list_ritual_history(cursor,limit) | Ограниченные страницы completed/missed экземпляров |
| get_ritual_summary() | Число совместных выполнений и 30 дней календаря UTC |
| can_read_ritual(ritual) | Caller-scoped boolean для RLS |

Private helpers `ritual_clock`, `validate_ritual_terms`, `ritual_context`, `lock_couple_ritual`, `materialize_ritual`, `close_rituals_on_departure` недоступны PUBLIC/anon/authenticated. Clock seam существует только для owner-controlled disposable тестов, клиент не выбирает время. JSON имеет строгие ключи/типы, ≤10 KB, лимиты текста и days; нельзя передать user_id, status, процент или вознаграждение. Read-only audit: `supabase/tests/ritual-privileges.sql`.

Порядок блокировок: advisory user → space row → ritual row → consent/instance. Он совместим с leave/tasks/goals/store. Два выполнения, решения, изменения и выход сериализуются по space. Исключение на любой стадии, в том числе COMMIT-time constraint trigger, откатывает всю транзакцию. Нет записей в reward_ledger, goal_reward_ledger, coin_transactions, user_progress или space_progress.

## Потерянные ответы и новые намерения

Формы сохраняют UUID + полный payload + исходный expected counter одним intent отдельно по user/scope в sessionStorage, с memory fallback. Retry не меняет условия или счётчик. Создание сверяет исходный activation payload даже после последующего редактирования текущих terms. Same-key replay проверяется до свежего fence/status и не создаёт второе предложение. Новый UUID со старого снимка отвергается; counters определяет сервер, они не являются источником игровых значений.

После неизвестного результата доступны read-only «Проверить прежний запрос», затем отдельно явный resend исходного intent, либо явное новое действие после обновления истории. Reconnect не отправляет proposal/complete автоматически; mutation retry отключён и offline вызов отклоняется сразу. Refresh может лениво создать **сегодняшний согласованный** экземпляр — это часть расписания, не новое предложение/согласие.

После полной потери и storage, и памяти UUID не восстановить. Требуется проверить историю перед отдельным новым предложением; сервер защищает stale counter, но не запрещает намеренно создать отдельный одинаковый ритуал с актуальным counter. Для MVP максимум 50 pending/active/paused ритуалов на пространство; closed/declined не входят в лимит. Это также ограничивает сегодняшний блок максимум 50 карточками.

## Приватность и история

Чтение требует, чтобы caller был одним из двух исходных участников и **оба** исходных человека сейчас находились в том же пространстве. Поэтому история с другим партнёром не появляется ни у нового участника, ни в общем текущем счётчике оставшегося. После выхода факты сохранены в БД, но недоступны, пока исходная пара не восстановлена. Возвращение того же человека разрешает читать старую историю, но не открывает закрытые ритуалы. Новый партнёр не получает прежние title/description/UUID/даты/отметки/агрегаты. Исторический Together XP остаётся пространству по прежним правилам, но ритуалы его не меняют.

Leave trigger в той же транзакции закрывает pending/active/paused исходной пары, void ожидающие согласия и переводит unfinished instances в missed. Completed и собственные отметки сохраняются. Ни один из участников не становится администратором. Административное удаление Auth-аккаунтов/retention не является пользовательской функцией: каскады разрешают только очистку собственных новых disposable fixtures в тестах.

Карточки и история имеют серверную live keyset pagination: list `(created_at,id)`, history `(scheduled_on,id)`, limit 1–50, по умолчанию 20. Cursor привязан к actor, текущим membership UUID, фильтру (для list) и time ceiling. Leave/rejoin/new partner инвалидируют старый cursor, даже если люди те же. Строгий MVCC snapshot не обещается: поздние COMMIT/смена фильтра могут потребовать обновить историю с начала. Нет offset или загрузки всех экземпляров ради первой страницы. История сначала ограничена пространством и индексом `(space_id,scheduled_on DESC,id DESC)`, затем проверяет исходную пару.

TanStack keys включают user id/epoch/filter; смена Auth очищает cache, create/accept/leave его сбрасывают. Polling 15 секунд обновляет согласования/текущий день; ошибки и mismatch epoch скрывают карточки. Уже прочитанные данные в сохранённой offline-вкладке нельзя удалённо отозвать; сервер не выдаёт по старому cursor новые данные. Summary возвращает только count и 30 календарных значений, без рейтинга и новых серий активности. Он O(доступной истории); при больших объёмах потребуется измеренная серверная агрегация.

## Проверки

Обязательные: `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. `npm test` включает UI/unit и **реальный disposable PostgreSQL 17** с исходными Auth/task/store/goal/statistics регрессиями. Покрыты создание/принятие/отказ, строгие inputs, исходные request replay/fences, edit snapshots, pause/resume/close/withdraw, две независимые отметки, concurrent mark/leave, lock-wait midnight и weekly/year boundary, отсутствие catch-up/начислений, COMMIT rollback, cross-space/new partner/rejoin, курсоры, grants и старый прогресс до миграции.

`npm run test:supabase -- <LOCAL_STATUS_JSON>` на свежем выделенном local Supabase дополнен настоящими JWT/RLS/RPC ритуалов, consent, duplicate marks, нулевыми изменениями экономики/статистики, историей и выходом/повторным вступлением. Использует только собственные новые временные локальные Auth-аккаунты и проверяет их очистку. Подготовка описана в `supabase.md`; status с локальными ключами хранится вне repo и удаляется.

Дополнительный browser smoke без новых npm dependencies:

```sh
npm run build
npm run preview -- --host 127.0.0.1 --port 4173
# В другом терминале, нужен установленный Chromium:
npm run test:ritual-browser
```

`CHROMIUM_BIN` при необходимости задаёт путь к системному Chromium. Скрипт разрешает только loopback demo preview, создаёт собственный временный профиль, проверяет 390×844 и 768×844 в обеих темах, пять вкладок, отсутствие горизонтального overflow и read-only примеры на Today/Us. Сохраняет screenshots в указанный `/tmp/kolo-ritual-browser-*`, закрывает только собственный browser. Это **не** двухаккаунтный browser E2E: реальные consent/RLS проверяются native Supabase runner, формы/ошибки/recovery — jsdom UI tests. Hosted Dashboard/SMTP и реальные аккаунты не проверяются.

## Развёртывание и ограничения

Новых env/secrets/Dashboard-настроек/cron нет. После отдельного разрешения владельца: проверить project ref/backup, `db push --dry-run`, применить **только pending** migration, проверить read-only grants audit, обновить типы штатным CLI и выполнить тестовый двухаккаунтный checklist. На большой базе согласовать окно для транзакционного создания индексов. Не reset, не переписывать применённые миграции, не удалять существующие аккаунты. Если кто-то уже применил раннюю версию pending SQL вне disposable среды, нужна отдельная forward migration. Setup/frontend/CI ничего удалённо не применяют.

MVP: нет cron/backfill пропусков, уведомлений, редактирования истории, undo отметки, повторного открытия closed, автоматического согласия, XP/Coins, нативных SDK или новых платных механик. Содержание/расписание редактируется целиком новым согласием; pending временно блокирует отметки. Calendar — только созданные экземпляры, а не выдуманные пропуски. Максимум 50 незакрытых ритуалов; длинные list/history доступны страницами. PR оставить открытым без merge.

### Результаты этого PR

Успешны typecheck, lint (без предупреждений), **114 UI/unit + 108 PostgreSQL tests** (102 security/RPC + 6 полных store migration), production build и browser smoke. PostgreSQL включает 14 тестов ритуалов поверх существующих 88, сохранность pre-migration пользователя и реальную конкурентность. EXPLAIN на 3 000 экземпляров / 6 000 отметок подтвердил `ritual_instances_history` для глубокой страницы пространства (~0,05–0,1 мс в текущем runner, не production SLA). Проверен иной DateStyle соединения — ISO period key не меняется.

Локальный полноценный Supabase smoke прошёл с настоящими PostgreSQL 17.11 / GoTrue 2.197 / PostgREST 16.4 / Mailpit, всеми прежними сценариями и ритуалами. Только новые собственные временные локальные пользователи; очистка проверена. Chromium проверил 390×844 и 768×844 в обеих темах и отсутствие горизонтального переполнения demo. Двухаккаунтного browser E2E нет. Сохраняется предупреждение Vite о большом общем JS chunk (~803 kB / gzip ~227 kB); разделение bundle — отдельная оптимизация.
